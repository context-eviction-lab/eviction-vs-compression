# Pilot Proposal — When Do Compression Methods Differ?

Nov 25, 2026 · @Angela

Tonight's pilot tests one question: **do compression methods only separate when a task depends on a fact that appears once?** It uses one small model, two tasks and four methods, and should fit on a single GPU in a few hours.

## Question and hypothesis

Standard benchmarks are too easy: strong methods already match the full model at 256–512 tokens, so they cannot be told apart.

- **Hypothesis H1:** on a *repetitive* task, all methods stay near full-model accuracy even at small budgets.
- **Hypothesis H2:** on a *single-fact* task, methods diverge sharply as the budget shrinks, and random eviction collapses first.

If H2 holds, the single-fact task design is a candidate benchmark for the team.

## Setup

| Item | Choice |
| --- | --- |
| Model | Qwen2.5-1.5B-Instruct (fits on one free Colab T4 or any 16 GB GPU) |
| Eviction library | NVIDIA `kvpress` (ships random, SnapKV, StreamingLLM and more behind one interface) |
| Compression library | `llmlingua` (LLMLingua-2) |
| Samples | 100 per task per setting |
| Budgets | keep 10%, 25%, 50% of the context, plus full (100%) |

## Tasks

1. **Single-fact task (synthetic).** Take about 2,000 tokens of filler text, such as past experiment summaries or Wikipedia. Hide one key fact at a random position ("The learning rate used in run 47 was 0.0031"), then ask for it. Exact-match accuracy. Generated by script, so no hand labelling.
2. **Repetitive task.** GSM8K maths problems with a long worked example in the prompt. Accuracy on the final number.

## Methods

| Method | Type | Where it cuts |
| --- | --- | --- |
| Full context | Baseline | Nothing removed |
| Random eviction | Simple floor | KV cache, at random |
| SnapKV | Heuristic eviction | KV cache, keeps tokens with high attention from the question |
| LLMLingua-2 | Prompt compression | Input text, before the model reads it |

Learned eviction (e.g. ForesightKV) is left for later; it needs training.

## Measurements

- **Accuracy vs budget** for each method and task, with 95% bootstrap confidence intervals (resample the 100 questions 1,000 times).
- **Paired comparison:** on the same questions, how often method A is right where B is wrong (McNemar-style counts). This is far more sensitive than comparing two averages.
- **Optional, entropy probe (Mike's idea):** for the single-fact task, record the model's average surprise (−log probability) over its answer tokens, with and without the fact deleted. Check whether higher surprise lines up with wrong answers.
